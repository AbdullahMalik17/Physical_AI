# Chapter 4: Simulation Fundamentals

## Introduction

**Why simulate?** Real robots are expensive, break easily, and can be dangerous during development. Simulation environments let you iterate rapidly, test edge cases safely, and validate algorithms before touching hardware. This chapter introduces simulation platforms and the critical **Sim-to-Real** transfer challenge.

:::info Learning Objectives
By the end of this chapter, you will understand:
- Why simulation is essential for Physical AI development
- The three major simulation platforms (Gazebo, Isaac Sim, MuJoCo)
- Physics engine fundamentals
- The Sim-to-Real gap and how to bridge it
- Setting up your first simulated robot in ROS 2
:::

## The Case for Simulation

### Real-World Constraints

| Constraint | Real Robot | Simulation |
|------------|------------|------------|
| **Cost per Iteration** | High (wear, breakage) | Zero (infinite resets) |
| **Iteration Speed** | Slow (setup, charging) | Fast (parallel instances) |
| **Safety** | Risk of injury/damage | Perfectly safe |
| **Data Collection** | Limited by time | Unlimited samples |
| **Edge Cases** | Hard to reproduce | Easy to script |
| **Parallelization** | 1 robot = 1 test | 1000 robots = 1000 tests |

### The Development Pipeline

```
1. Develop in Simulation → Fast iteration, safe testing
2. Validate in Simulation → Edge cases, stress tests
3. Transfer to Real Robot → Final validation
4. Iterate (Sim + Real) → Close the Sim-to-Real gap
```

## Simulation Platforms Comparison

### 1. Gazebo (Classic & New)

**Best for:** General robotics, ROS 2 integration, mobile robots

**Strengths:**
- ✅ Native ROS 2 support
- ✅ Free and open-source
- ✅ Large community, many robot models
- ✅ Good physics (ODE, Bullet, Dart)

**Weaknesses:**
- ❌ Graphics not photorealistic
- ❌ Limited sensor simulation (cameras, LIDAR basic)
- ❌ Slower than specialized simulators

**Use Case:** Wheeled robots, arms, basic humanoids

### 2. NVIDIA Isaac Sim

**Best for:** Humanoids, photorealistic rendering, AI training

**Strengths:**
- ✅ Photorealistic graphics (RTX ray tracing)
- ✅ PhysX GPU-accelerated physics
- ✅ Advanced sensor simulation (depth, LIDAR, IMU)
- ✅ Domain randomization built-in
- ✅ ROS 2 integration

**Weaknesses:**
- ❌ Requires NVIDIA GPU (RTX recommended)
- ❌ Steeper learning curve
- ❌ Heavier resource requirements

**Use Case:** Humanoid robots, vision-based AI, Sim-to-Real transfer

### 3. MuJoCo

**Best for:** Reinforcement learning, contact-rich tasks

**Strengths:**
- ✅ Extremely fast physics
- ✅ Accurate contact dynamics
- ✅ Popular for RL research
- ✅ Free since 2021 (Google acquisition)

**Weaknesses:**
- ❌ No ROS integration by default
- ❌ Basic rendering
- ❌ Requires custom tooling

**Use Case:** RL training, manipulation research, fast simulation

### Recommendation

| Your Goal | Recommended Platform |
|-----------|---------------------|
| **Learn ROS 2** | Gazebo |
| **Humanoid AI** | NVIDIA Isaac Sim |
| **RL Research** | MuJoCo |
| **Quick Prototyping** | Gazebo |
| **Production Deployment** | Isaac Sim + Real Hardware |

## Physics Engine Fundamentals

### What Physics Engines Simulate

1. **Rigid Body Dynamics**
   - Position, velocity, acceleration
   - Mass, inertia, center of mass

2. **Collision Detection**
   - Bounding boxes, meshes
   - Contact points and normals

3. **Contact Forces**
   - Friction (static, dynamic)
   - Restitution (bounciness)
   - Damping (energy loss)

4. **Joint Constraints**
   - Revolute (hinge), prismatic (slider)
   - Spherical (ball), fixed
   - Spring-dampers

### Physics Engine Comparison

| Engine | Speed | Accuracy | Stability | Used By |
|--------|-------|----------|-----------|---------|
| **ODE** | Medium | Medium | Medium | Gazebo (default) |
| **Bullet** | Fast | Good | Good | Gazebo, Pybullet |
| **PhysX** | Very Fast (GPU) | Excellent | Excellent | Isaac Sim, Unity |
| **Dart** | Medium | Excellent | Excellent | Gazebo (alternative) |

### Time Steps and Stability

**Simulation Equation:**
```
dt = simulation_time_step (e.g., 0.001s = 1ms)
real_time_factor = dt_sim / dt_real

Example:
If 1 second of simulation takes 2 seconds real time:
real_time_factor = 1.0 / 2.0 = 0.5x (slower than real-time)
```

:::warning Critical Concept
**Smaller time steps = More accurate but slower**

- **1 ms (0.001s)**: Standard for robotics
- **0.1 ms**: High-precision control
- **10 ms**: Fast preview, less accurate

Rule: Time step should be 10x smaller than fastest dynamics
:::

### Spawning in Gazebo

**spawn_robot.launch.py:**
```python
from launch import LaunchDescription
from launch_ros.actions import Node
from launch.actions import ExecuteProcess
import os

def generate_launch_description():
    # Path to URDF file
    urdf_file = os.path.join(
        os.getcwd(),
        'my_robot.urdf'
    )

    # Read URDF
    with open(urdf_file, 'r') as f:
        robot_desc = f.read()

    return LaunchDescription([
        # Start Gazebo
        ExecuteProcess(
            cmd=['gz', 'sim', '-r', 'empty.sdf'],
            output='screen'
        ),

        # Spawn robot
        Node(
            package='ros_gz_sim',
            executable='create',
            arguments=[
                '-name', 'simple_bot',
                '-topic', '/robot_description',
            ],
            output='screen'
        ),

        # Publish robot description
        Node(
            package='robot_state_publisher',
            executable='robot_state_publisher',
            parameters=[{'robot_description': robot_desc}],
            output='screen'
        ),
    ])
```

### Controlling the Simulated Robot

```python
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Twist

class SimulatedRobotController(Node):
    def __init__(self):
        super().__init__('sim_robot_controller')

        # Publish to Gazebo velocity command topic
        self.publisher = self.create_publisher(
            Twist,
            '/model/simple_bot/cmd_vel',
            10
        )

        # Move in a square
        self.create_timer(2.0, self.move_forward)
        self.create_timer(8.0, self.turn_left)

    def move_forward(self):
        cmd = Twist()
        cmd.linear.x = 0.5  # 0.5 m/s forward
        self.publisher.publish(cmd)
        self.get_logger().info('Moving forward')

    def turn_left(self):
        cmd = Twist()
        cmd.angular.z = 0.5  # 0.5 rad/s left turn
        self.publisher.publish(cmd)
        self.get_logger().info('Turning left')

def main(args=None):
    rclpy.init(args=args)
    node = SimulatedRobotController()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()
```

### Python API Example

```python
from isaacsim import SimulationApp

# Start Isaac Sim
simulation_app = SimulationApp({"headless": False})

from omni.isaac.core import World
from omni.isaac.core.robots import Robot
from omni.isaac.core.utils.stage import add_reference_to_stage
import numpy as np

# Create world
world = World()

# Add ground plane
world.scene.add_default_ground_plane()

# Load humanoid robot (Carter wheeled robot as example)
robot_path = "/Isaac/Robots/Carter/carter_v1.usd"
add_reference_to_stage(robot_path, "/World/Carter")

# Create robot object
robot = world.scene.add(Robot(prim_path="/World/Carter", name="carter"))

# Reset world
world.reset()

# Simulation loop
for i in range(1000):
    # Step physics
    world.step(render=True)

    # Apply simple control (move forward)
    if i % 100 == 0:
        velocities = np.array([2.0, 2.0])  # Left, right wheel
        robot.set_joint_velocities(velocities)

# Cleanup
simulation_app.close()
```

## The Sim-to-Real Gap

### Sources of Sim-to-Real Gap

1. **Physics Approximations**
   - Simplified contact models
   - Ignored effects (air resistance, cable drag)
   - Discrete time steps

2. **Sensor Differences**
   - Perfect vs. noisy sensors
   - Ideal vs. real camera characteristics
   - Latency and synchronization

3. **Actuator Modeling**
   - Instantaneous vs. real motor response
   - No backlash, flex, or wear
   - Perfect vs. imperfect control

4. **Environmental Factors**
   - Simplified lighting and textures
   - No temperature, humidity effects
   - Perfect vs. variable surfaces

### Bridging the Gap

**Strategy 1: Domain Randomization**
```python
# Randomize simulation parameters to cover real-world variation
randomization_params = {
    'mass': (0.8, 1.2),  # ±20%
    'friction': (0.5, 1.5),
    'lighting': (300, 3000),  # Lux
    'camera_noise': (0.0, 0.05),
    'latency': (0.0, 0.05),  # seconds
}
```

**Strategy 2: System Identification**
```python
# Measure real robot parameters and update simulation
real_robot_params = measure_real_robot()
simulation.update_parameters(real_robot_params)
```

**Strategy 3: Residual Learning**
```
Policy_real = Policy_sim + Residual_correction

Train Policy_sim in simulation
Train Residual_correction on real robot (few samples)
```

**Strategy 4: Progressive Transfer**
```
1. Train in idealized simulation
2. Add noise and randomization
3. Validate in simulation with real parameters
4. Test on real robot with safety limits
5. Fine-tune on real robot
```

### Validation Metrics

```python
def sim_to_real_validation(sim_performance, real_performance):
    """
    Compare simulation vs. real-world performance

    Returns:
        gap_score: 0 (perfect transfer) to 1 (total failure)
    """
    gap = abs(real_performance - sim_performance) / sim_performance
    return gap

# Example
sim_success_rate = 0.95
real_success_rate = 0.82
gap = sim_to_real_validation(sim_success_rate, real_success_rate)
print(f"Sim-to-Real gap: {gap*100:.1f}%")  # Output: 13.7%
```

:::tip Best Practices
**Minimize Sim-to-Real Gap:**
1. Measure and match real robot physics parameters
2. Add sensor noise models
3. Use domain randomization during training
4. Validate incrementally (sim → sim with noise → real)
5. Keep controllers simple and robust
6. Test edge cases in both sim and real
:::

## Benchmarking Your Simulation

```python
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Pose
import time

class SimulationBenchmark(Node):
    def __init__(self):
        super().__init__('sim_benchmark')

        self.start_time = time.time()
        self.sim_steps = 0
        self.poses = []

        # Subscribe to robot pose
        self.create_subscription(
            Pose,
            '/robot/pose',
            self.pose_callback,
            10
        )

        # Benchmark timer
        self.create_timer(10.0, self.report_performance)

    def pose_callback(self, msg):
        self.sim_steps += 1
        self.poses.append(msg)

    def report_performance(self):
        elapsed = time.time() - self.start_time
        real_time_factor = self.sim_steps * 0.001 / elapsed  # Assuming 1ms steps

        self.get_logger().info(
            f'Performance Report:\n'
            f'  Simulation steps: {self.sim_steps}\n'
            f'  Real time: {elapsed:.2f}s\n'
            f'  Real-time factor: {real_time_factor:.2f}x\n'
            f'  Steps/second: {self.sim_steps / elapsed:.0f}'
        )

def main(args=None):
    rclpy.init(args=args)
    node = SimulationBenchmark()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()
```

## Hardware-in-the-Loop (HIL) Simulation

### Concept

**Connect real sensors/actuators to simulation:**
```
Real Camera → Simulation (processes image) → Real Motors
```

**Benefits:**
- Test real sensor noise
- Validate motor response
- Gradual transition to full hardware

**Example Setup:**
```python
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Image
from geometry_msgs.msg import Twist

class HILController(Node):
    """
    Hybrid controller: real camera, simulated planning, real motors
    """
    def __init__(self):
        super().__init__('hil_controller')

        # Real camera input
        self.real_camera_sub = self.create_subscription(
            Image, '/real_camera/image', self.camera_callback, 10
        )

        # Simulated planning output
        self.sim_cmd_pub = self.create_publisher(
            Twist, '/sim/cmd_vel', 10
        )

        # Real motor output
        self.real_motor_pub = self.create_publisher(
            Twist, '/real_robot/cmd_vel', 10
        )

    def camera_callback(self, msg):
        # Process real camera image
        # Run simulated planning
        # Send commands to real motors
        cmd = self.plan_motion(msg)
        self.real_motor_pub.publish(cmd)
```
